# Музейный маршрут — Москва

Опубликованный прототип каталога музеев, карты, календаря событий и публичной Telegram-ленты по заданию из IDEA.md. Данные настоящие: локальные выгрузки 2ГИС/Яндекс.Карт и доступные страницы сайтов. Демонстрационные события не добавлялись.

## Запуск

```powershell
python serve.py
```

Открыть http://127.0.0.1:8765. Сервер отдаёт только `web/`, исходные базы и служебные файлы через него недоступны. Остановка — Ctrl+C. Можно указать другой порт: `python serve.py --port 8766`. Для просмотра готовой копии достаточно Python; установка зависимостей нужна только сборщику.

На сайте работают поиск по имени, адресу и теме; фильтры по тематике и формату музея; фильтр наличия Telegram; сортировка А–Я/Я–А, по тематике и формату; карточки с контактами; карта с точками; календарь недели, месяца и года; выбор дня; фильтр типа события; экспорт текущего периода в .ics; до пяти последних доступных публикаций каждого канала; скачивание CSV и JSON.

Результат первого сбора 9 октября 2026 года: 1 270 записей-кандидатов, 980 записей с сайтом, 1 269 с координатами. Проверено 554 домена, 468 отдали хотя бы одну HTML-страницу. После объединения повторных событий найдено 76 датированных программ из двух сайтов; большая часть — «Булгаковский Дом». Это узкое покрытие расписаний, а не полная московская афиша. Найдено 363 различных Telegram-ссылки, у 306 доступны публичные посты; сохранено 1 500 публикаций. Telegram-ссылки не все являются официальными музейными каналами.

Фильтры общие для каталога, карты, календаря и Telegram. Один музей может относиться к нескольким темам. Тематика предварительная, по названию; исходный список не является проверенным реестром действующих музеев. Числа и покрытие сбора показаны в разделе «Источники» и `data/collection-report.json`.

## Идея и приоритет MVP

Идея жизнеспособна: единая точка поиска снижает необходимость обходить десятки афиш вручную. Основная сложность — поддержание достоверного расписания и каталог филиалов, а не интерфейс календаря. Разумный первый выпуск: полный каталог кандидатов плюс проверенные афиши 20–30 наиболее востребованных музеев. Затем расширять покрытие с измерением свежести и ошибок.

Для прототипа приняты следующие допущения: Москва и Зеленоград, без Московской области; музейные площадки и музеи-квартиры сохраняются отдельно; школьные и ведомственные музеи пока включены; чтение публичных Telegram-страниц без входа; бесплатный поиск и просмотр без регистрации; локальный запуск. Для этого этапа уточнения не блокировали работу. Перед публичным выпуском нужно определить, включать ли закрытые для свободного посещения школьные/корпоративные музеи, кто проверяет события и какой нужен график обновления.

## Варианты реализации

Оценки ниже — ориентир планирования для одного разработчика, при доступных источниках. День означает примерно 8 рабочих часов. Это не фактически затраченное время текущей сессии. Ручная проверка всех записей и нестандартные сайты увеличат оценки.

| Вариант | Стек | MVP | Плюсы и ограничения |
|---|---|---|---|
| **1. Статический сайт + сборщик — выбран** | Python, requests, BeautifulSoup, JSON/CSV, HTML/CSS/JS, Leaflet | 16–24 часа / 2–3 дня | Простой запуск и размещение; не нужен постоянно работающий backend. Обновление отдельной командой; нет редакторской панели. |
| 2. Приложение с базой и редактором | Python/FastAPI, SQLite → PostgreSQL, React, Leaflet, планировщик | 40–64 часа / 5–8 дней | Проверка дублей, правки тематик, история событий, автоматические обновления. Больше сопровождения. |
| 3. Редакторский каталог | Django, PostgreSQL, встроенная админка, шаблоны/HTMX, фоновые задания | 48–80 часов / 6–10 дней | Удобно регулярно проверять события и площадки. Требует сервера и настройки доступа редактора. |

Рекомендация: начать с варианта 1, затем перейти к варианту 2 или 3, если ежедневное обновление и ручная редактура окажутся востребованы. Наполнение расписаниями 20–30 приоритетных музеев: ещё 24–48 часов; широкое покрытие сотен разных сайтов: ориентировочно 80–160 часов и больше. Ручная проверка каталога: 12–24 часа для первичного прохода, сложные дубли и доступность площадок отдельно. Поддержка после запуска: ориентир 2–6 часов в неделю, зависит от частоты изменений сайтов.

## Классификация

Писатели и литература; искусство и архитектура; военная история; наука и техника; природа и естествознание; музыка, театр и кино; транспорт; быт, ремёсла и гастрономия; история и культура; религия и духовная культура; спорт; интерактивные и необычные; другие / требуют уточнения.

Правила находятся в `src/services/classify.py`. Это объяснимая стартовая разметка, а не экспертная атрибуция. Формат «музей-квартира» независим от темы: можно выбрать квартиры писателей или музыкантов. Для ручной правки внесите в `data/theme-overrides.json` объект вида `{"id_музея": ["Писатели и литература"]}` и пересоберите данные. ID можно взять из `web/data/catalog.json`. Художественный музей имени Пушкина специально отделён от литературных музеев.

## Сбор и обновление

```powershell
python -m pip install -r requirements.txt
$env:PYTHONUTF8='1'
python scripts/collect.py --workers 6
```

Сборщик обходит все известные домены, главную и до трёх связанных страниц контактов/афиши/новостей; затем проверяет известные публичные Telegram-ссылки. Результат сохраняется после каждого домена и канала в JSONL. По умолчанию повторный запуск продолжает сбор, пропуская сохранённые результаты, включая ошибки. Для нового полного сбора:

```powershell
python scripts/collect.py --refresh --workers 6
```

Для ограниченной проверки доступны `--limit 30 --telegram-limit 20`. Новая сборка готового сайта без сетевых запросов:

```powershell
python scripts/build_data.py
```

Повторное извлечение исходного каталога на этой машине:

```powershell
python C:/Users/Yuri/.codex/skills/maps-2gis-yandex/search_maps.py --rubric "Музеи,Музей" --region "Москва" --dedup none --out data/raw/museums.jsonl
python scripts/import_maps.py
python scripts/build_data.py
```

Импорт дополнительно отбирает музейные подрубрики и город, нормализует название и адрес; разные филиалы не схлопываются по домену. Обе базы имеют несовпадающие названия и адреса, поэтому остаточные дубли требуют редакторской проверки. Записи вне географии/подрубрики сохраняются отдельно в `data/raw/excluded.jsonl`. Дата импорта не является датой свежести исходной базы.

Ключи и LLM для этого прототипа не требуются. При добавлении поиска недостающих сайтов используйте XMLRiver в отдельном `src/services/xmlriver_client.py`, локальный `.env`, таймауты и сохранение каждого результата. Существующие базы и сайты уже дали материал для MVP; полнота сайтов всех московских музеев не заявляется. Недостающие сайты не угадывались.

## Риски и границы прототипа

- Справочники содержат дубли, школьные музеи и закрытые площадки. Доступность сайта не подтверждает доступность музея. Следующий этап — таблица ручной сверки и статус посещения.
- Расписание: универсальный сборщик читает только JSON-LD Event, в том числе вложенную разметку. Сайты без неё представлены ссылками на афишу, без выдуманных дат. Нужны отдельные адаптеры для популярных музеев и проверка отмен.
- Разметка сайтов тоже может быть ошибочной или устаревшей. У даты сохраняются источник и время сбора; время без часового пояса трактуется как московское при экспорте. Если сайт указал только день, время не придумывается.
- Музейный домен может обслуживать несколько филиалов. События связываются с общим сайтом и явно помечены: место нужно проверить у организатора. Сайт агрегатора может содержать сторонние события — подключать его к надёжной афише следует после ручной проверки.
- Контакты из справочника могут быть устаревшими; найденные на общем сайте могут относиться к головной организации. Telegram-ссылка может вести в бот, личный профиль или посторонний канал. Лента показывает только те ссылки, у которых доступны публичные публикации; официальность требует проверки.
- Публичные Telegram-страницы могут не отдавать последние пять постов целиком, либо быть заблокированы. Показываются до пяти реально доступных публикаций, а не гарантированная полная история.
- Сейчас обновление запускается вручную. Автоматическое расписание и мониторинг ошибок ещё не настроены. Для размещения нужны условия использования источников и выбор хостинга; сайт опубликован на GitHub Pages: https://wwwparser.github.io/moscow-museums-site/.
- Карта использует Leaflet с локальными JS/CSS, подложка OpenStreetMap требует интернета. Для массового публичного трафика надо выбрать подходящего поставщика тайлов.

Для production хранить музеи, филиалы, источники, каналы, события и связи раздельно в базе; не назначать каждое событие всем филиалам. Обновлять популярные афиши несколько раз в день, остальные ежедневно, контакты еженедельно; это предложение, не текущая настройка.

## Проверки и документация

```powershell
python -m unittest discover -s tests -v
python scripts/verify_data.py
node --check web/app.js
python -m compileall -q src scripts serve.py
```

Правила карты сверены с [документацией Leaflet](https://leafletjs.com/reference.html), модель датированного события — с [Schema.org Event](https://schema.org/Event). Telegram предусматривает [виджет публичных постов](https://core.telegram.org/widgets/post); прототип использует сохранённый текст публичной страницы и ссылку на оригинал, без входа в аккаунт. Официальная документация Leaflet на дату работы описывает также новую alpha-версию; здесь закреплена стабильная библиотека 1.9.4 с лицензией в `web/vendor/LEAFLET-LICENSE`.

Проверено в браузере: поиск, сочетание темы и формата, сортировка, открытие карточки, 1 269 точек на карте, календарь недели/месяца/года, поиск по названию события, выгрузка .ics, Telegram-лента и мобильная ширина 390 пикселей без горизонтального переполнения. Четыре теста парсинга проходят; скрипт проверки подтверждает уникальность ID, ссылки между музеями и событиями, корректность дат, не более пяти постов на канал и отсутствие дублей постов.


## Публикация и обновление через агента

Сайт: https://wwwparser.github.io/moscow-museums-site/
Репозиторий: https://github.com/wwwparser/moscow-museums-site

Для календаря созданы 554 конфигурации источников в `data/event-profiles.json`, включая 17 индивидуальных адаптеров HTML, JSON API и AJAX. Общий парсер остальных сайтов требует сверки: его даты помечены в интерфейсе. Результат проверки каждого сайта виден в разделе источников; «Нужен адаптер» не означает отсутствия событий. Ошибка загрузки сохраняет прежние даты с отметкой об устаревании; исчезновение со страницы не считается подтверждённой отменой. Исключённые при проверке общие афиши отмечены в конфигурации `calendar_enabled: false`.

```powershell
python scripts/monitor_events.py --workers 6 --days 90
python scripts/monitor_events.py --dedicated-only --refresh
python -m unittest discover -s tests
python scripts/verify_data.py
```

Сбор сохраняется после каждого источника. Повторный запуск пропускает проверенные в последние 12 часов сайты. `--refresh` запускает проверку принудительно; `--domains` выбирает домены через запятую. Даты без года принимаются только отдельными адаптерами текущих афиш и помечаются. Периоды программ отделены от сеансов; перечисленные дни сохраняются без выдуманных ежедневных повторов. История изменений остаётся локально в `data/event-history.jsonl`.

После проверки агент коммитит изменения и запускает `powershell -File scripts/publish.ps1`. Файлы из `web/` публикуются в ветке `gh-pages`; исходный код хранится в `main`. Постоянный фоновый мониторинг не установлен: сбор запускается агентом по запросу. Свежие числа показаны на сайте и в `data/collection-report.json`; первоначальные 76 программ выше относятся к первому проходу до добавления адаптеров.
